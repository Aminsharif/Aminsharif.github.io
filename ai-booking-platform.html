Case Study

AI Booking Platform — AI Appointment Scheduling & Calendar Automation

An AI booking assistant that talks to customers in natural language — by web, chat, and inbound phone call — checks real Google Calendar availability, books, reschedules and cancels appointments, stores everything in PostgreSQL, and sends confirmations and reminders. It runs on one n8n engine with a Vapi + Twilio voice line, exposed via a FastAPI backend with a Next.js dashboard.

  • n8n
  • FastAPI
  • PostgreSQL + pgvector
  • Google Calendar
  • Vapi + Twilio Voice
  • Next.js

Problem & Solution

Problem

  • Manual phone/email scheduling wastes staff hours and creates double bookings
  • Customers must be available during business hours to book
  • Availability spread across a calendar, business hours, and a spreadsheet
  • No-shows from missing confirmations and reminders
  • Missed and after-hours phone calls lose bookings entirely
  • One-off scripts that drift between the web UI and chat channels

Solution

  • Natural-language AI agent that books, checks, reschedules, and cancels
  • One unified n8n operations engine shared by the web UI and every chat channel
  • Google Calendar as the source of truth for availability, synced both ways
  • Idempotent bookings with hard double-booking protection and buffers
  • An inbound phone line (Vapi + Twilio) that books by voice, 24/7, under the same rules
  • Email confirmations plus a reminder runner with retry and error handling
  • FAQ/policy answers from a section-aware RAG knowledge base
  • Next.js dashboard for bookings, availability, schedule, services, and users

The n8n Workflows

Bookings created from the web dashboard and from every chat channel run through one engine in n8n. A web-facing Operations API authenticates the caller and routes each operation to the same sub-workflows the AI agent uses — so availability, double-booking protection, Google Calendar sync, and confirmation emails behave identically everywhere.

WF0 — Operations API (web + external)

Webhook /ops
Webhook — Operations API POST /webhook/ops
Authenticate Caller X-Ops-Token header
Route by Operation WF2 · WF3 · WF4 · WF5
Idempotency Key Check pending hold → finalize
Uniform Response Envelope { success, operation, data, error }

The single front door for the web dashboard and external callers. It authenticates with a shared token, routes each operation to the same sub-workflows the AI agent calls, holds a pending slot and immediately finalizes it, and always answers with one predictable envelope.

WF1 — Incoming Conversation (AI Agent)

Chat channels
Web · Telegram · WhatsApp · Gmail Triggers omnichannel
Normalize to One Message Shape Code
Guardrails — Off-topic & Confirmation keyword safety
AI Agent (DeepSeek) tool loop · 7-msg memory
Tools — services · availability · booking · knowledge $fromAI schemas
Grounded Reply never invents slots

Every channel is normalised into one shape, screened by deterministic guardrails, then answered by a tool-calling agent that only acts on real availability. The agent never invents slots — it offers exactly what check_availability returns.

WF2 / WF3 / WF4 — Booking, Availability & Read Core

Deterministic SQL
check_availability (WF3) weekly slot schedule
Apply Duration · Buffer · Holidays · Notice · Window booking rules
Merge Calendar Events + DB Bookings busy intervals
create_booking (WF2) idempotent + conflict guard
Create Google Calendar Event → Confirm source of truth
Read Tools (WF4) — services · settings · appointments read-only SQL

Availability is read from a persistent recurring weekly slot schedule, then narrowed by service duration, buffers, holidays, minimum notice, maximum booking window, external calendar conflicts, and existing database bookings. The agent only ever sees what this engine computes.

WF5 — Reschedule & Cancellation

Ownership-checked
Find Appointment reference / id
Ownership Check customer email / phone
Re-check Conflicts no double-booking
Update / Delete Calendar Event Google Calendar API
Cancel Pending Reminders → Re-schedule status: rescheduled / cancelled

A leaked token can't touch someone else's booking: reschedule and cancel additionally require the booking's own email or phone. Calendar events and reminder rows move together with the appointment status, so records never drift.

WF6 / WF7 / WF8 — Knowledge RAG Engine

Additive
WF7 Ingest — faq · text · pdf · url versioning + dedupe
Section Detection → Parent / Child Chunks 500–800 / 150–300 tok
Embeddings → pgvector OpenAI / Ollama
WF6 Search — pgvector + Postgres FTS parallel top-k
RRF Fusion → Parent Expansion grounded context
WF8 Admin — list · stats · toggle · reindex tenant-scoped

Business knowledge — policies, refunds, location, payments, terms — is answered by a section-aware parent/child RAG pipeline. It is strictly additive: the deterministic booking engine stays the only source of truth for services, hours, prices, and appointments.

Reminders & Error Handling

Scheduled + event-driven
Cron — Every 5 Minutes reminder runner
Reclaim Stuck → Claim Due Reminders Postgres locking
Send Confirmation / Reminder Email per reminder rule
Error Trigger → Classify & Sanitize attempt log

A scheduled runner claims due reminders, reclaims stuck jobs, and retries failures, while an error handler classifies and sanitises every failure with a retry decision and attempt log behind it.

Voice Phone Booking — Vapi + Twilio

Customers can call a real phone number and book, reschedule, or cancel out loud. A Twilio number carries the inbound call into Vapi, which runs the speech-to-text, LLM, and text-to-speech stack and drives the very same n8n operations engine the web and chat channels use — so a phone booking follows identical availability, double-booking protection, Google Calendar sync, and confirmation rules.

Inbound Call → Booking Flow

WF11 · /webhook/vapi
Caller Dials the Twilio Number telephony
Vapi Answers — Deepgram STT nova-2 · multi-language
Voice LLM — GPT-4o with Booking Tools live date + time
ElevenLabs Text-to-Speech natural spoken replies
Tool Call → n8n /webhook/vapi X-Vapi-Secret auth
Parse & Authorize → Build Ops Request Code node
WF0 → WF2 / WF3 / WF4 / WF5 same engine as web + chat
Spoken Result + Confirmation Email reference read back slowly

The phone call never touches booking logic directly. Vapi translates each spoken intent into an operations request, WF11 authenticates it and forwards it to WF0, and the result is spoken back — so the voice line inherits the exact same rules as every other channel and nothing in WF0–WF10 had to change.

Voice Assistant Behaviour & Safety

Prompt + guardrails
Caller ID Becomes the Phone Number automatic
One Service → Use It; Several → Ask Which get_services once
Offer Up to 3 Real Slots never invents times
Spell Email Letter-by-Letter → Read Back spoken confirmation
Explicit “Yes” Before Any Mutation create / reschedule / cancel
Ownership Verification for Changes booking reference + email
Idempotency Key vapi:<callId>:<start_time> retry-safe

A dedicated voice prompt keeps replies short and natural, asks for one thing at a time, and handles English or Bangla. Because a retried tool call can't double-book (the idempotency key is derived from the call id and the slot) and changes require the booking's own email, a phone call is as safe as the web flow.

Results

What This System Automates

  • Customers book, reschedule, or cancel in natural language across the web widget, Telegram, WhatsApp, Gmail, and an inbound phone line
  • A Vapi + Twilio voice assistant answers real phone calls 24/7, offers only verified slots, and books with the same rules as every other channel
  • One n8n operations engine serves the dashboard, chat channels, and the voice line, so behaviour never drifts between front doors
  • Availability is computed from a persistent weekly schedule plus Google Calendar conflicts, buffers, notice, and business rules
  • Idempotent booking with a pending-hold → finalize flow makes retries and webhook replays safe from double-booking
  • Confirmations and reminders go out on schedule, with stuck-job reclaim and a retry/error pipeline behind them
  • FAQ and policy questions are answered from a section-aware RAG knowledge base without touching booking data
  • A Next.js dashboard gives admins bookings, calendar, schedule, services, knowledge, settings, and user management

No performance metrics have been invented here — measurable numbers will be added once live production usage produces them.
