The problem and how I solve it

What goes wrong

  • A general chatbot gives confident answers that do not match your real policies
  • Knowledge is scattered across PDFs, wikis, tickets and drives
  • Keyword search misses the question when the wording differs
  • Nobody can tell where an answer came from, so it cannot be trusted

What retrieval changes

  • Answers are composed only from passages found in your own content
  • Sources are listed, so any answer can be verified in seconds
  • Keyword and semantic search run together to catch both exact terms and meaning
  • When nothing relevant is found, the system says so rather than inventing

How a knowledge base is built

Your documents, pages and records are collected as the knowledge source
Content is cleaned, split into passages and turned into embeddings
A question is searched with hybrid retrieval — keywords plus meaning
The best passages are reranked so only the most relevant are kept
An answer is written from those passages and cites its sources

What is included

  • A knowledge source built from the documents you already have
  • A repeatable ingestion pipeline that keeps the index current
  • Hybrid retrieval combining keyword and semantic search
  • Reranking so the strongest passages reach the model first
  • Answers that cite the document they came from
  • An API or widget that drops into the tools you already use
  • Testing against real questions before launch

Related work: this is the same retrieval layer used by the multi-tenant knowledge platform and the document Q&A pipeline case studies.

Frequently asked questions

How is this different from a chatbot that just talks?
A plain chatbot answers from what the model already learned. A retrieval-augmented system first searches your own documents and answers from the passages it finds, so the response is tied to your real, current content and can cite where it came from.
Will it make things up?
The system is designed to answer only from retrieved content. When a good match cannot be found it says so instead of guessing, and confidence thresholds can route the question to a person.
What kinds of documents can it read?
Help centres, PDFs, policies, product documentation, internal wikis, support tickets and database records are all common sources. What can be ingested depends on the formats and systems you already use.
Do we have to re-upload everything when documents change?
No. An ingestion pipeline can update only what has changed, so new and edited documents are reflected without rebuilding the whole knowledge base each time.
Can it live inside our own product?
Yes. The retrieval layer can be exposed as an API so your own application, support desk or internal tools query it directly, rather than running as a standalone chat window.
Which models and database does it use?
The design is model-agnostic. It commonly runs with an OpenAI-compatible model and PostgreSQL with pgvector, but a managed vector store or a different model can be used depending on your constraints.
